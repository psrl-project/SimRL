## 1. 问题怎么定义

同步或低 staleness 的 RL，一个 rollout 窗口的长度由最慢的那批请求决定：

```
窗口 ≈ max( 主体 token 数 / 主体吞吐 ,  最长请求长度 × 它所在 batch 的每 token 时间 )
```

两项分别受不同旋钮控制：

- 主体吞吐随 batch 变大而上升，所以大 cap、小 TP 有利。
- 每 token 时间随 batch 变大而上升，所以小 cap、大 TP 有利于长请求。

同构 fleet 只能在两者之间折中。异构并行的想法是把两类请求拆开，各自运行在合适的区间。
三篇论文和我们的工作都是在这个框架下，只是约束、信号和算法不同。

### 2.2 Heddle

**要解决的问题。** 把 rollout makespan 分解成 `max_i ( T_queue + N_tokens · T̄ · α + T_tool )`，其中 `α` 是并发带来的干扰系数。token 数和工具耗时视为不可优化，剩下三个旋钮对应三个决策：何时调度（排队）、放在哪里（干扰）、用多大 MP（基础每 token 时间）。

**长度预测。** 在 (context, 剩余长度) 上微调一个 0.6B 回归模型，每个 agent 步骤结束后重新预测，与工具执行并行，所以不在关键路径上。论文强调第二步的预测比第一步准，因为上下文在积累。相比"只看 prompt"的模型法和历史统计法，长尾召回和 Pearson 相关都更高。

**调度。** 优先级等于预测长度，越长越先。再加引擎里的抢占：新请求若比正在跑的最低优先级请求更重要，就把后者踢回队列，保留它的前缀 KV。

**放置。** 引理：存在最优划分，每组都是按长度排序后的连续区间。于是用 DP：
`dp[i][j] = min_k max( dp[k][j-1], L(τ_{k+1}) · T · F(组) )`，复杂度 O(n²m)，n=6400、m=16 时约 42 ms。
`F` 是干扰系数，只取决于组大小，由 profiler 加模拟器给出。预测被修正后，按活跃轨迹数缩放各组容量并迁移，迁移用 RDMA 传 KV，藏在工具调用的空档。

**异构 MP 的分配。** 对 {N_1…N_m}（总和等于 GPU 数）做排序初始化的模拟退火，扰动有重分配、拆分、合并三种，每个候选用上面的 DP 评估，整个过程约 5 秒。映射规则是分组按长度降序、worker 按 MP 降序，最长的一组去 MP 最大的 worker。

**结果。** 对 Verl 1.4–2.3x，对 Slime 1.2–2.5x。分项消融：调度 1.1–1.26x，放置 1.2–1.5x，异构资源 1.1–1.3x。基线是轮询调度、同构 MP、每 worker 固定 batch 100。

**局限。** 工具调用空档是迁移免费的前提，单轮推理没有。

### 2.3 Libra

**两个机制。**
1. 全局资源规划器加弹性混合池：在固定 GPU 预算下联合决定训练与 rollout 各用多少卡、每个 rollout 实例用什么 TP，目标是最小化 `T_iter = max(T_rollout, T_train)`。
2. C-MLFQ 路由：所有请求先进最小 TP 的桶，每次工具返回时查因果前缀树决定要不要迁移。

**长度信息。** 分两层，都不是参数化预测器：
- 规划器用每个 prompt 的历史长度（每次 rollout 完成后更新），按长度排序后喂给 DP。
- 运行时路由用前缀树。键是 prompt 加工具返回状态序列（工具类型、payload 大小、成功或失败），节点存剩余长度的均值和 P90，**两者落在同一个桶才迁移**。未见过的节点回退到父节点。策略漂移时重建树即可，不需要重训模型。

**规划算法。** 对按长度升序排序的请求，每个 TP 实例负责一段连续区间：
`dp[g][i] = min over tp∈{1,2,4,8}, x of max( dp[g−tp][i−x], Cost(tp, i−x+1, i) )`，
`Cost` 来自类似 Vidur 的代价评估器，用多项式拟合（误差 3–6%）。训练侧用决策树枚举 (TP, PP, DP)，规划器每隔若干步重新运行，收益超过重配置代价才触发。

**弹性。** 核心训练池拓扑不变，混合 worker 以完整未分片的数据并行副本身份加入或退出。训练到 rollout 的切换要 10.8 s，反向 3.6 s 快照加 4.4 s 重载，非阻塞，总开销低于 3.5%。

**结果与消融（R2E-Gym，Qwen3-14B，吞吐 tok/s）：**

| 步骤 | 吞吐 | 增量 |
|---|---|---|
| 均匀切分基线 | 423 | |
| 规划器，同构 TP | 510 | +20% |
| 加异构 TP | 551 | +10% |
| 加 C-MLFQ | 666 | +27% |
| 加弹性 | 763 | 累计 +80% |

路由对比（Search-R1，相同异构桶）：负载均衡 1502，MLFQ 1917，预测式 2289，C-MLFQ 2700，Oracle 3102。逐决策准确率为 31.2、44.8、65.2、91.1、100%。
头条的 3.0x 是对 colocated 基线，对 AReaL 的最优静态划分只有 1.38–1.63x。

**局限。** 迁移依赖工具调用空档做 CPU 卸载。Libra 自己的图 3 说 TP8 在 16–32k 比 TP1 快 2.8x，但原因是 A800-80GB 上 Qwen3-14B 的 TP1 受 KV 压力限制，这个比例不能直接搬到别的硬件。

### 2.4 TailSieve

**核心论断。** 即使已知所有长度，最优路由也不是均匀的：最优解把少数极长请求隔离到一个低并发的尾副本，再给它一点平衡流量，使两个副本的完成时间相等。**平衡的是完成时间，不是请求数。**

**长度信息的来源。** 不预测。上一轮在截断点还没跑完的 prompt 组，下一轮被当作尾部候选。依据是 prompt 的长尾倾向在相邻几轮更新间稳定（排序 AUC 大于 0.95，prompt 解释 64.8% 的长度方差）。截断点设在 5%、10%、25% 时捕获 85%、93%、95% 的真实长尾组。候选从头重新生成，不复用 token，所以保持 on-policy。

**算法。**
- 离线最优对照：Bellman 式 DP 加 Pareto 剪枝，把 2^100 压到 10^6–10^7。
- top-k 隔离：最长的 k 条放尾副本，对 100 个真实 rollout 组，最优 k 与精确最优解差距在 4% 以内。
- 在线两层控制器：内环用 `q* = N · r_tail / (r_bulk + r_tail)` 均衡两池完成时间。外环比较两池的边际容量 `M = γ/(αλ)` 决定移动副本，每次最多动一个，并在半径 2 内检查非单峰性。

**完成时间模型。** `T = Σ_j τ(j) · (L_j − L_{j+1})`，`τ` 是随 batch 增长的每 token 时间。它和我们的排空模型是同一个。

**额外的一块。** 尾副本是低并发、长解码，非常适合投机解码，而隔离防止了投机验证拖慢高并发的主体副本。可以给两个池配不同的投机深度（总预算相同时，主体 3 加尾部 5 对比对称的 4 加 4）。

**结果。** 纯路由 1.11–1.67x（35B 在 KodCode 上最高）。加 MTP 或 DFlash 后最高 2.59x。端到端 GRPO，2B 模型路由 1.45x（119.3 s 降到 82.5 s），加 MTP 2.56x。控制器从不同初值收敛到相同的 (q, m) = (4, 2)。

**与我们最接近。** 它的场景（单轮、GRPO 组为路由单元、无工具）和我们一致。它的"异构"是池的**副本数**，不是 TP。

### 2.5 三篇的对照结论

- **只有 TailSieve 的场景和我们相同。** Heddle 与 Libra 都依赖工具调用提供的信号和免费迁移窗口，这在单轮推理里不存在。
- **三篇的在线信号都不是"预测每条请求的最终长度"。** Heddle 用逐步更新的估计，Libra 用因果状态，TailSieve 用上一轮的 prompt 级信号。这不是巧合，见第 4 节洞见 6。
- **各篇的头条数字都包含了弱基线。** Heddle 的基线没有调 cap，Libra 的 3.0x 是对 colocated。拆开看，纯"异构并行加路由"的收益在 Libra 里约 1.31x（510 到 666），Heddle 里 1.1–1.3x，TailSieve 里 1.12–1.67x，与我们的 1.0–1.36x 同一量级。
- **三篇都没做的事：** 把 TP4 当尾层、把 TP 度数和长度分层一起规划（Libra 的 DP 做了 TP 选择，但没有考虑混合）。
- **我们没做而它们做了的：** 跨阶段 GPU 划分与弹性（Libra 里最大的单项）、引擎级抢占式优先级（Heddle）、路由专用投机解码（TailSieve 里最大的单项）。

## 3. 我们做了什么

### 3.1 实验基础设施

- 仿真器：`policy=psrl`，composed cost model（实测 kernel 表），8 个权重版本，staleness 0、1、2。
- 新增 TP4 与 TP8 的 GEMM、attention、elementwise 表（collective 表复用已有的 world size 2、4、8），KV 容量实测：TP4 233 万、TP8 477 万 token。
- 每个对比都要求消费的轨迹数与 token 数相同。
- 基线是一组梯度：no-cap、最优 cap、同构加调度（LPT 或 makespan 放置）。

### 3.2 cap 敏感度（异构之前的铺垫）

cap 只能通过 decode 吞吐影响 span，所以敏感度有上限，约 1.6x（4 个版本）和 1.8x（16 个版本）。三个因素压低它：

| 因素 | 现象 |
|---|---|
| 长度离散度 | 均值 4k 的 lognormal，CV 0.3、0.6、1.0、1.5 对应 1.41x、1.34x、1.22x、1.05x |
| 训练下限 | 训练约 137 us/token，rollout 一旦比训练快，cap 不再有影响 |
| KV 上限 | b 超过 KV / 峰值 context 后只增加 preemption |

最敏感的构造：每条 response 3072 token、prompt 32 token，1.61x，解析上界 1.72x。

### 3.3 TP 的物理

低负载、长 context：8 张卡跑 8 条 30k 的请求。

| 布局 | 每 token 延迟 | 每 GPU 吞吐 |
|---|---|---|
| 8×TP1 | 8.19 ms | 122 tok/s |
| 4×TP2 | 7.33 ms | 136 tok/s |
| 2×TP4 | 6.38 ms | 157 tok/s |
| 1×TP8 | 6.01 ms | 166 tok/s |

高负载、短 context：2k context、每 GPU 64 条，TP1 3079、TP2 2626、TP4 2514、TP8 2134 tok/s/GPU。

TP 越高，每卡读的权重越少，这份读取由 batch 内请求分摊，所以低负载时 TP 越高越好。负载高了，权重读取已被摊薄，不随 TP 缩小的固定开销（kernel launch、elementwise、all-reduce，约 3.5 ms）成为主导。**延迟杠杆在 TP4 基本用尽，TP8 只比 TP4 快约 6%。**

### 3.4 异构分层的结果

构造 workload：每步 512 条请求，508 条 4096 token，4 条 32768 token。8 卡 `[TP4, TP1×4]`，训练 DP=4，比值为基线 span 除以异构 span：

| 基线 | S=0 | S=1 | S=2 |
|---|---|---|---|
| no-cap | 1.33x | 1.38x | |
| 最优 cap | 1.29x | 1.20x | 0.94x |
| 同构 + 调度 | 1.25x | 1.18x | 0.93x |

其余格子：主体更重（6k、8k）时纯分层会输到 0.76–0.87x，混入短请求后回到 1.12–1.19x。16 卡 1.32–1.36x。TP8 层不比两个 TP4 层好。训练慢（DP=1）、宽尾分布（dapo_32k）、straggler 数过少或过多时收益消失。

### 3.5 平凡分布

8 卡，batch 64，对"同构 + 调度"：

| 分布 | S=0 | S=1 |
|---|---|---|
| lognormal CV 1.0 | 1.05–1.08x | 1.03x |
| lognormal CV 0.6 | 1.05x | 1.02x |
| dapo_32k | 1.01x | 1.00x |

对 no-cap 则是 0.99–1.18x。**平凡分布下，大部分收益来自长度感知调度，不是异构本身。**

### 3.6 `TierPlanner`

每个权重版本重新规划一次，输入是上一版本遗留的 partial rollout 加即将放行的新 prompt 组，输出 TP 形状、tier 的长度区间和 cap。三种求解器共用一个排空模型。

| 求解器 | 10 个格子几何均值 | 单次耗时 |
|---|---|---|
| `twopool` | 1.075x | 约 20 ms |
| `pp` | 1.066x | 约 90 ms |
| `dp` | 1.056x | 约 800 ms |

三者几乎相同，说明最优结构只有两层，DP 多出来的自由度没有用上。

### 3.7 长度信息的价值

对"同构 + oracle 调度"的加速比范围：

| 长度信息 | 范围 |
|---|---|
| oracle | 1.00–1.25x |
| 噪声预测器 σ=0.25 | 0.93–1.20x |
| σ=0.5 | 0.80–1.09x |
| σ=1.0 | 0.67–0.93x |
| 在线估计（prompt 历史、生存、总体分位数） | 0.28–0.93x |

## 4. 洞见

1. **基线决定结论。** 对默认路由的同构 fleet，异构看起来能赢 1.4x 以上。加上 cap 调优后是 1.2–1.3x，再加上同构 fleet 上同样的长度感知调度，只剩 1.0–1.25x。三篇论文的头条数字都没有这层对照，对比时必须逐项拆开。

2. **异构并行不是通用加速，它只在一个窄区间有收益。** 需要同时满足：每步有少量（约 4–8 条）远长于主体的 straggler，主体足够多让 TP1 处于高负载，rollout 在关键路径上（训练够快），staleness 不超过 1。平凡分布两头都不满足：长请求要么太少（lognormal CV 0.6 每步约 1 条）要么太多（dapo_32k 约 130 条）。

3. **必须有 TP4，TP2 不够。** TP2 的延迟优势只有 1.12–1.35x，撬不动权衡。只用 TP1 与 TP2 时，异构相对同构加调度只多约 1%。

4. **用一部分 GPU 的吞吐换关键路径的延迟。** 尾层的 4 张卡只产出约 6% 的 token，看起来浪费，但它们在关键路径上。往尾层混入短请求能平衡两侧，但代价比直觉大：4 条长请求加 8 条短请求，每步慢 23%，加 32 条慢 44%。混入是平衡杠杆，不是额外加速。

5. **最优结构是"尾部隔离加均衡"，不需要 DP。** 三篇论文和我们的结果一致：两层加完成时间均衡就够，top-k 在精确最优 4% 以内，DP 只在需要第三层或每层选 TP 时才有价值。

6. **长度信息的质量比算法重要，而且漏判不对称。** 漏掉一条 straggler，它会落到高负载 TP1 上，单条就决定窗口，误报只是浪费一点尾层空间。所以预测器要保召回，不是保精度。三篇论文都回避了"预测每条的最终长度"，转而用逐步更新的估计、因果状态或上一轮的 prompt 级信号。

7. **S=0 时事后补救来不及，S=1 才有空间。** rescue（请求长出所在 tier 后重新放置）在 S=1 有帮助，在 S=0 不起作用，因为伤害发生在前几步。S=2 时 staleness 预算吸收了 straggler，问题退化成吞吐问题，同构更好。

8. **cost model 之外的结构性约束。** 固定开销约 3.5 ms 不随 TP 缩小，决定了 TP8 不值得，KV 容量决定了 cap 上限，训练速度决定了 rollout 是否在关键路径上。三者都不是调度算法能改变的。

## 5. 方法论教训

| 教训 | 代价 |
|---|---|
| 同构 cap 网格必须越过最优点 | 第一版网格的最优在边界，扩展后比值从 1.38x 降到 1.29x |
| 对照组必须包含"同构 + 同样的调度" | TP1、TP2 阶段把调度收益误记成异构收益 |
| 先确认消费的轨迹数和 token 数相同 | 提前结束的 run 会得到虚高的速率 |
| 共享节点测 kernel 必须全程监控 GPU，测完复查日志 | 我曾在没复查日志时声称"测量期间无外来进程"，复查后发现 TP4 elementwise 受污染，之后 TP8 初测也被污染，偏差最大 34% 与 2.3x，都已重测 |
| 借用 kernel 表要 `cp -a`，不要 `ln -s` | `fit-floor` 顺着符号链接覆盖了仓库里的 `floors.json`，原件无法重新生成 |
| 并行仿真不要 `conda activate` | 几百个并发激活在锁上排队，238 个 conda 进程对 36 个仿真 |
| 手算带宽估计会严重偏乐观 | "塞 32 条短请求只慢 13%"，实测 44% |
| 模型预测要和仿真对账 | 预测 makespan 与仿真窗口的比值 0.86–0.94。cap 用闭式处理时，仿真窗口在 265 s 与 326 s 之间跳动，比预测慢约 30%，改成事件驱动后窗口稳定在 260 s |
| 一个分支不触发时，先问"和不开它逐位相同吗" | rescue 因使用过期的空位计数，在 S=0 下静默地从不触发 |

## 6. 局限与待做

**局限。**
- 全部是仿真，cost model 在 TP4、TP8 上没有端到端对账，只有 kernel 表本身的拟合质量。
- 单 seed，没有置信区间。比值在 0.99–1.06 之间的差异不应被解读。
- 构造 workload 是为了找到收益区间，真实 RL 的长度分布更接近第 3.5 节。
- 没有多轮工具调用场景，Heddle 与 Libra 依赖的信号无法检验。

**值得做，按预期价值排序。**
1. 路由专用投机解码：TailSieve 里最大的单项（路由 1.12–1.67x，加 MTP 后最高 2.59x），尾层低并发、长解码正好适合，而且和 TP 分层正交。
2. 更大的模型（14B 或 32B）：权重占更多 HBM，TP1 更受 KV 限制，Libra 的 TP1 与 TP8 差距主要来自这一点。
3. 跨阶段 GPU 划分与弹性：Libra 里最大的两项，rollout 与训练的 GPU 比例目前固定。
4. 把 TailSieve 的"partial rollout 作尾部过滤器"做成估计器，替换 oracle，并在 prompt 历史稳定的 trace 上验证召回率。
5. 对旧 `ParallelismSolver` 的取舍：它的 SCG 目标仍有测试依赖，是否删除需要决定。
